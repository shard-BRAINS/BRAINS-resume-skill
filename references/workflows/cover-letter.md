# Workflow: Cover Letter Generation

**Purpose:** Generate a cover letter matched to a tailored resume and job description. The letter is composed to complement — not duplicate — the resume, using evidence from the user's experience to address the role's must-haves and close with a clear, forward-looking call to action.

---

## Trigger Conditions

Start this workflow when any of the following is true:

- The user has a tailored (or original) resume plus a target JD and wants a cover letter.
- The user has just completed the tailor workflow and accepts the offered next step in step (j) of that workflow.

---

## Inputs to Collect

Before beginning, confirm every input below:

1. **Resume** — the tailored version if a tailor pass was completed; otherwise the original. If a structured output file was generated by a prior workflow, read from it directly. If not, parse via `scripts/parsers/pdf_to_text.py` or `scripts/parsers/docx_to_text.py` as appropriate.
2. **JD source** — accept one of:
   - Pasted plain text or markdown
   - URL: fetch and parse via `scripts/parsers/jd_url_fetch.py`
   - Screenshot: read directly; Claude can parse image text
3. **Recipient name and title** (optional) — improves personalisation of the salutation and close.
4. **Personal hook** (optional) — a specific reason for interest, a connection to the employer's work, or a detail the user wants threaded through the letter. If not supplied, use generic-but-specific structure. **Do not invent a hook.**
5. **Disclosure stance** — carry over from the current session. If not established, ask before proceeding.

---

## Procedure

**(a) Parse resume and JD content.**
Use the resume data collected in Inputs step 1. If the JD was supplied as a URL, run `scripts/parsers/jd_url_fetch.py` to retrieve clean text. If pasted or screenshot, proceed directly. Extract the role title, employer name, must-have requirements, and any culture or mission language from the JD.

**(b) Check saved career preferences against the JD.**
Compare the role, employer ecosystem, and extracted requirements against all memory entries before composing any content. If the JD conflicts with a saved preference — for example, the role sits in an ecosystem the user has explicitly excluded — **stop immediately**. Surface the conflict and ask whether to abort or proceed with a documented exception. Never silently comply.

**(c) Compose a draft three-paragraph letter.**
Structure the letter as: hook → fit → close. Apply the per-paragraph calibration below:

- **Hook** — open with the role title, employer name, and one concrete reason for interest. Apply Pattern 8 calibration: include one first-person motivation signal backed by a specific (a named project type, a stated professional goal, a sector the user has genuine experience in). If no personal hook was supplied, use the role's scope or the employer's domain as the anchor — do not fabricate.
- **Fit** — present 3–4 evidence points that directly connect the user's experience to the JD must-haves. Each evidence point must be a claim paired with a measurable outcome (metric, scope, or demonstrable result). Do not use P1 vocabulary (pattern-one ND-disclosure terms) regardless of disclosure stance.
- **Close** — forward-looking and brief. Confirm availability and interest in next steps. Do not over-specify (no invented timelines or salary signals). Keep it action-oriented; avoid formulaic sign-off language.

**(d) Apply disclosure-stance reconciliation.**
Review the full draft against the user's disclosure stance before presenting it:

- **Non-disclosure:** no ND identity language, no advocacy signals, no terms associated with neurodivergent disclosure. Remove any that appear.
- **Neutral signalling:** ND-associated strengths (depth of focus, systems thinking, pattern recognition) may be present; do not name or frame them as ND identity.
- **Explicit disclosure:** ND identity may be named where it arises naturally and the user has indicated they want it present. Do not force it into unnatural positions.

**(e) Run validators on the draft.**
With the draft assembled, run:
- `scripts/validators/bias_scan.py` — flag ND-disclosure-relevant patterns not covered by the user's disclosure stance
- `scripts/validators/integrity_check.py` — check for prompt-injection patterns, structural anomalies, or data integrity warnings

Stop on any CRITICAL finding and require explicit user sign-off before continuing.

**(f) Present the draft and collect per-paragraph decisions.**
Show the full draft to the user. Walk through each paragraph in order and prompt: accept, reject, or modify. Record every decision; do not apply changes silently or in batches. If a revision request would require fabricating employer-specific knowledge the user has not supplied, decline the fabrication and offer a structurally equivalent alternative grounded in what is known.

**Template selection.** This workflow defaults to the `formal-business` cover-letter template. Before rendering, walk the user through `references/template-selection.md` to decide whether `formal-business` or `modern-clean` better fits the target industry. Pass the chosen template name as the `template=` argument to the generator.

**(g) Render output files.**
Call `scripts/generators/cover_letter_to_docx.py` and `scripts/generators/cover_letter_to_pdf.py` with the finalised letter content. Apply the timestamped naming convention (see Output Artifacts below).

**(h) Offer the bias-aware ATS-check workflow.**
Present the option to run the bias-aware ATS-check workflow on the cover letter and resume together before submission.

## Output Artifacts

| File | Notes |
|---|---|
| `output/cover-letter-{slug}-YYYY-MM-DD-HHMMSS.docx` | Unbranded — the user's submitted document |
| `output/cover-letter-{slug}-YYYY-MM-DD-HHMMSS.pdf` | Unbranded — the user's submitted document |

`{slug}` is a kebab-case fragment derived from the JD title and company name (e.g., `senior-engineer-example-corp`). Strip or replace all characters that are not alphanumeric or hyphens. Use the same slug as the corresponding tailored resume if one exists.

---

## Boundaries

These rules are non-negotiable:

- **Never fabricate employer-specific knowledge.** If the user did not supply a personal hook, do not invent one. Use generic-but-specific structure anchored in the role or domain.
- **Never fabricate experience.** Each evidence point in the fit paragraph must map to work the user has genuinely done.
- **Surface career-preference conflicts; never comply silently.** Any conflict with a memory entry stops the workflow at step (b).
- **Never override disclosure stance.** Reconcile every draft against the user's stated stance in step (d) without exception.
- **User-veto principle.** No paragraph content is finalised without explicit acceptance in step (f).
- **Cover letters are unbranded artifacts.** The DOCX and PDF carry no BRAINS identity.
